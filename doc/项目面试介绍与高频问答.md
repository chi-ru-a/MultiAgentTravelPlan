# planMultiAgent 多 Agent 旅行助手：项目面试介绍与高频问答

## 1. 项目一句话介绍

> 这是一个基于 FastAPI、LangGraph 和 LangChain 的多 Agent 旅行助手。用户通过聊天提出班次、天气或旅行规则问题，Supervisor 负责意图识别和任务拆分，多个专业 Worker 可以并行调用工具，最后通过 SSE 流式返回综合答案。

## 2. 90 秒项目介绍

> 我做的是一个多 Agent 旅行助手，主要解决一个用户问题中可能同时包含班次、天气和政策咨询等多个子任务的问题。系统入口是 FastAPI 的 SSE 聊天接口，用户输入消息后，Supervisor 先进行关键词匹配，复杂或多意图场景再调用大模型判断需要哪些 Agent。班次、天气、知识库和闲聊分别由不同的 ReAct Worker 负责，多个 Worker 通过 LangGraph Send 并行执行，结果再由 Synthesizer 汇总并流式返回前端。
>
> 技术上，LangGraph 负责主工作流和并行 fan-out/fan-in，LangChain 负责 Tool、ChatOpenAI 和 ReAct Agent 适配，FastAPI 负责接口和 SSE，React 负责聊天界面。知识库 Agent 的 RAG 链路是先调用 Embeddings 服务生成查询向量，再访问 Qdrant 或 Elasticsearch 做相似度检索，最后让 Agent 根据召回片段回答。需要说明的是，当前仓库没有内置知识文档和导入流程，因此 RAG 代码是接入骨架；班次查询也仍然使用模拟数据。
>
> 当前方案适合作为多 Agent 架构示例。若继续生产化，我会优先补充知识文档导入、错误状态区分、持久化会话、鉴权、限流和真实业务服务接入。

## 3. 架构和数据流

```text
用户
  -> React
  -> FastAPI SSE
  -> Supervisor
  -> 一个或多个 ReAct Worker
  -> Tool
  -> Agent 输出
  -> Synthesizer
  -> SSE 前端
```

主要 Agent：

| Agent | Tool | 当前数据来源 |
| --- | --- | --- |
| `ticket_search` | `TicketSearchTool` | 固定模拟数据 |
| `weather_search` | `WeatherSearchTool` | 智谱搜索，失败时部分模拟数据 |
| `kb_search` | `KnowledgeBaseTool` | Qdrant/ES + Embeddings，需预先有文档 |
| `chitchat` | `ChitchatTool` | LLM |

## 4. 高频问题与参考回答

### Q1：为什么这是多 Agent，而不是多个 Tool？

Tool 是具体能力，例如查询天气或查询班次；Agent 是带有角色 Prompt、LLM 和 Tool 的执行单元。项目通过 `create_react_agent` 为每个领域工具创建 Worker Agent。Supervisor 决定调用哪个 Agent，Agent 再决定如何调用绑定的 Tool。

因此可以理解为：

```text
Tool = 能力函数
Agent = LLM + 角色 + Tool + 执行决策
Supervisor = Agent 调度器
```

### Q2：LangGraph 在哪里发挥作用？

它不是只作为依赖存在，而是直接用于：

- 定义 `AgentState`；
- 创建主工作流；
- 注册 Supervisor、Worker 和 Synthesizer 节点；
- 使用 `Send` 并行分发任务；
- 使用 reducer 聚合并行结果；
- 使用 `MemorySaver` 保存进程内会话状态。

### Q3：Qdrant 没安装，为什么仍然能路由到知识库 Agent？

路由只由 Supervisor 根据关键词和 LLM 决定，不会先检查 Qdrant 是否可用。因此“改签规则”仍会命中 `kb_search`。真正执行检索时才访问 Embeddings 和 Qdrant；基础设施不可用时，当前 service 会捕获异常并返回空结果，Tool 通常表现为“未找到相关信息”。

### Q4：当前项目有真正的 RAG 数据吗？

仓库有 RAG 检索代码和 `add_document/add_documents` 服务方法，但没有内置知识文档、导入脚本或知识库管理路由。因此当前项目具备 RAG 接入能力，但没有开箱即用的知识内容。必须先将文档切分、向量化并写入配置的 collection。

### Q5：Qdrant 和 Embeddings 分别负责什么？

Embeddings 服务把文本转换成向量；Qdrant 保存向量并做相似度检索。查询时先把用户问题向量化，再去 Qdrant 找相似文档片段。二者缺一不可，除非改用 Elasticsearch 或其他向量方案。

### Q6：为什么不把所有工具直接绑定给一个 Agent？

当前按领域拆分可以让每个 Agent 的 Prompt 更短、工具边界更清晰，也便于展示并行执行。比如班次 Agent 不需要理解知识库检索参数，天气 Agent 也不需要处理退票政策。

### Q7：多任务如何实现并行？

Supervisor 返回多个 `next_agents` 后，工作流通过 LangGraph `Send` 为每个 Agent 创建分支。各分支执行完后，`agent_outputs` reducer 聚合结果，再由 Synthesizer 汇总。这样班次查询和天气查询不需要严格串行等待。

### Q8：当前班次是真实数据吗？

不是。`TicketService.search_tickets()` 当前直接返回 `_get_mock_data()` 的固定列表，`TICKET_API_URL` 的真实请求代码被注释。面试中应明确说是模拟实现，而不是声称已接入票务系统。

### Q9：当前天气是真实数据吗？

配置有效时会调用智谱联网搜索；搜索失败时，代码对部分城市返回固定模拟天气。因此它是“联网搜索 + 开发降级”，不能保证任何情况下都是实时天气。

### Q10：MemorySaver 能用于生产吗？

当前用法更适合单进程 Demo 或 MVP。它把会话放在进程内，重启会丢失，多实例之间也不会共享。生产环境应替换为 Redis、数据库或其他持久化 checkpointer，并配合会话过期和租户隔离。

### Q11：这个项目当前最大的技术债是什么？

主要有四个：

1. RAG 只有检索骨架，没有文档导入闭环；
2. Qdrant/Embeddings 异常会被转换为空结果，无法区分“无命中”和“服务不可用”；
3. 班次仍是模拟数据；
4. 会话、鉴权、限流和观测能力不足以直接支撑生产多实例部署。

## 5. 面试表达注意事项

- 不要说“每个 Tool 就是一个 Agent”，应说明 Agent 包装并调用 Tool。
- 不要说“项目已有完整知识库”，应说明当前只有 RAG 接口和检索实现。
- 不要说“班次已接入真实 API”，当前是模拟数据。
- 不要把 MemorySaver 描述成数据库持久化。
- 重点说明 Supervisor、Worker、Tool、Synthesizer 的职责边界，以及 Send 并行带来的架构价值。
